# 公共 Outbox 持久定时（B6a）

源码能力，尚非部署验收。三个实例继承本模板实现；本包不包含 Knowbase 的解析状态机。

## 调用与事务

`enqueue_task(..., not_before=aware_datetime)` 或 `OutboxEvent(not_before=...)`
声明最早可执行的绝对时间；省略保持原来的立即入队语义。必须带时区，统一成 UTC。
业务用例应从 PostgreSQL 时钟计算并持久化时间；**相同幂等键的恢复必须复用同一时间**，
不可每次重试都重新计算 `now + interval`。不同时间是不同意图，会拒绝复用幂等键。

不调用 broker countdown、不在 Worker 中 sleep。消费者 handler 把业务进度与下一条
定时消息写入当前 session，**不提前 commit**，随后由公共 runtime 同事务写 Inbox。
这样崩溃、提交失败、执行租约失效时三者一起回滚；中途自行 commit 的领域用例不会
自动得到这一更强保证。下一条消息必须具有自己的幂等键，但应沿用需要串行化的
topic/aggregate_key；不同 topic 的同名 aggregate 并不共用执行租约。

## 唯一意图与调度投影

最早时间编码在既有 `outbox_message.headers` 的保留项 `sunmoonai.not_before.v1`；
它属于不可变幂等意图。仅通过 `not_before` 参数设置，不能直接伪造保留 header；
持久化前重新校验 DTO，生成的元数据计入 header 数量和 256 KiB 大小限额。
没有新增状态表或迁移，也没有修改跨 App 的领域 DTO/schema。

`available_at` 初始化为该时间，但它是会随传输重试变化的调度投影，不是原始意图。
两条发布 claim 路径同时检查投影及最早时间；消费者只检查原始最早时间，不能用
available_at 阻断已成功发布的消费（现有发布完成会把 available_at 推到未来）。
判时采用数据库时钟。重放/对账可以重置 available_at，但不能提前原始意图。
未到期消息不领取执行租约、不扣发布次数；到期后仍受 pump 周期、队列、租约和容量影响，
这是“不早于”，不是精确时刻触发或完成时限。deadline、退避上限属于调用领域。

所有数据库写入者必须遵守保留 header 协议；绕过仓库直接写坏日期可能导致 SQL claim
报错，不能将该报错当成消息完成。直接 SQL 修复、历史数据检查与运维授权另行处理。

## 验证与启用边界

`tests/test_delivery_schedule.py` 使用现有可丢弃数据库 fixture，覆盖：未到期拒绝两条
发布路径及直接消费、到期执行、时区/幂等/大小限制、回执原子性、取消与租约失效、
重试、对账及死信重放。配合原有真实数据库故障回归执行，而不是只测 SQL 字符串。

旧消息无保留项，保持兼容；**旧消费者不理解新定时意图**。不得在旧、新运行角色混跑时
启用领域定时生产者；应先排空旧进程并统一升级，再启用调度生产者。回滚旧代码前先停止
新生产者、排空/对账所有仍被引用的定时消息，不删表清队列。源码测试不等于 KIND、
身份、容量、真实 broker、业务库检查或运行态回滚验收；这些仍是独立发布门禁。
